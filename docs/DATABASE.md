# Database and Storage

## Overview

The application uses Supabase PostgreSQL and Storage through same-origin server APIs. Production metadata, policies, grants, constraints, indexes, and buckets were inspected read-only on 2026-07-12 and rechecked during Batch 5 on 2026-07-15. The repository still lacks a complete historical migration chain, so future schema changes must be exported as authoritative migrations rather than inferred from this document.

The application does not create a Supabase Auth session. `/api/auth` authenticates the configured viewer/admin passwords and writes a signed HttpOnly Cookie; `/api/auth/session` exposes only the resolved role to the browser. Application data, including anonymous-message reads and writes, uses server routes backed by the server-only service-role client. The repository retains `SUPABASE_ANON_KEY` only for operator direct-access regression, not browser runtime access.

## Production tables

All listed production tables have RLS enabled.

### Diary

`diaryContent`:

| Field | Production type | Notes |
|---|---|---|
| `id` | `BIGINT` | Identity primary key |
| `date` | `DATE` | Unique; indexed descending as `idx_diary_date_desc` |
| `subtitle` | `TEXT` | Nullable; included in search |
| `content` | `TEXT` | Nullable in production, required by the TypeScript model |
| `modifiedAt` | `TIMESTAMP` | Nullable mixed-case field |
| `created_at` | `TIMESTAMPTZ` | Defaults to `now()` |
| `image_paths` | `JSONB` | Defaults to `[]`; TypeScript treats it as a string array |

`diary_AI_analysis` uses a `BIGINT` identity primary key plus nullable `diary_id`, `summary`, and `emotion`, with `created_at TIMESTAMPTZ DEFAULT now()`. Its foreign key to `diaryContent.id` uses `ON DELETE NO ACTION`; application code explicitly removes analysis rows before deleting a diary.

The application assumes one diary per date and handles PostgreSQL `23505`; production confirms the `diaryContent_date_key` unique constraint.

### Health and anonymous messages

`health_conditions` has `TEXT` primary key `id`, required `condition`, `start_date`, `end_date`, and `color`, plus nullable `created_at TIMESTAMPTZ DEFAULT now()`.

`anonymous_messages` has a `BIGINT` primary key, required `content`, required `created_at TIMESTAMPTZ DEFAULT now()`, nullable `user_agent`/`ip_address`, and a validated 1–2000-character trimmed-content check.

### Audio

`audio_messages` has a UUID primary key defaulting to `gen_random_uuid()`, required `title`, `author`, `date DATE`, `audio_path`, and `duration NUMERIC`, plus nullable `created_at TIMESTAMPTZ DEFAULT now()`.

### Yearly summaries

- `yearly_summaries`: integer primary key, unique required `year VARCHAR`, created/updated timestamps.
- `important_events`: integer primary key; required summary ID, start/end dates, description; indexed summary ID.
- `ai_analysis_sections`: integer primary key; required summary ID, title, content; indexed summary ID.
- `ai_analysis_opinions`: integer primary key; required section ID, content, analysis; indexed section ID.
- `yearly_images`: integer primary key; required summary ID, optional `storage_path`, required legacy `alt`, timestamps; indexed summary ID.

Production foreign keys from events, sections, and images to `yearly_summaries`, and from opinions to sections, all use `ON DELETE CASCADE`.

Application mutations resolve the URL year to `yearly_summaries.id` and scope every event, section, opinion, and image lookup to that ownership chain. A missing year or wrong-year child ID returns `404` before any database or Storage mutation.

### Other production tables

The inspected Supabase project also contains `diaryInfo` and `rss_articles`. Current application source does not query either table. `diaryInfo` is a preserved legacy keepsake: RLS is enabled with no policy and PUBLIC/anon/authenticated have no table or identity-sequence privilege, so only trusted service-role access remains. Because application login uses a custom Cookie rather than Supabase Auth, any future viewer/admin display must use a Cookie-authorized same-origin API. `rss_articles` belongs to another project and is intentionally out of scope for this repository.

## Private knowledge index

`supabase/migrations/20260719155837_knowledge_base_index.sql` was applied to production on 2026-07-20 as Supabase migration `20260720125016_knowledge_base_index`. The migration and independent postflight preserved all 595 source diaries.

The migration enables `extensions.vector` and creates three locked application tables:

- `knowledge_source_settings`: one row per diary, with `private`/`excluded` usage scope, indexed source hash/model, and last-indexed timestamp.
- `knowledge_chunks`: newline-first source excerpts with diary/date/title metadata, exact character offsets, SHA-256 content hash, embedding model, and `extensions.vector(1024)` generated by `Qwen/Qwen3-Embedding-0.6B`. Single and consecutive newlines have equal highest boundary priority. Adjacent short segments are balanced toward 400–700 characters with an 800-character hard maximum; a long line falls back to complete sentence endings, overlaps only a complete sentence of at most 120 characters, and finally uses a balanced hard split for an extreme sentence without punctuation. Newline cuts never overlap across the boundary. The current small corpus intentionally uses exact vector scans rather than an approximate HNSW/IVFFlat index.
- `knowledge_index_jobs`: one retryable queue row per diary with pending/processing/completed/failed state and a stale-processing reclaim window.

All three tables enable RLS with no browser policies and explicitly revoke PUBLIC/anon/authenticated privileges. The migration grants only `service_role` table/sequence access. Its `queue_diary_knowledge_index()` trigger records work after diary date/title/content changes without making external calls. `claim_knowledge_index_jobs()`, `replace_diary_knowledge_chunks()`, and `search_private_knowledge()` are `SECURITY INVOKER`, service-role-only functions; function EXECUTE is revoked from PUBLIC/anon/authenticated. The hybrid search keeps an empty function `search_path` and schema-qualifies pgvector cosine distance as `OPERATOR(extensions.<=>)`. Chunk replacement, source index metadata, and job completion occur in one database transaction.

The initial migration queued every existing diary. Indexing remains a separate administrator action: the server reads queued sources, hashes the date/title/content, skips unchanged model/hash pairs, requests document embeddings from the local Qwen3 FastAPI service, and calls the transactional replacement function. Local indexing uses `input_type: document` and sends at most 16 texts per request. Online query embeddings now come from the Cloudflare-hosted Qwen3 model and do not replace existing document vectors. The earlier production smoke test used ModelScope and indexed one source into one 1024-dimensional chunk; existing rows retain that history until the administrator explicitly queues a full rebuild. A chunking-rule-only source change does not alter the diary content hash, so applying the new segmentation requires “rebuild all” followed by sync. Deleting a diary cascades to settings, chunks, and its queue row. Emergency schema removal is documented in `supabase/rollbacks/20260719155837_knowledge_base_index_rollback.sql`; it retains the potentially shared `vector` extension and never removes source diaries.

Current local processing waits at least two seconds between sources. Worker source exposes knowledge status, search, and factual answers; the Fact Layer is deployed and accepted in production, while production continues to block index-maintenance POST requests with `409`. Sync, rebuild, and retry are performed only from the local Next.js development server while the separately maintained FastAPI service is running. The current operator workflow assumes no diary insert or update occurs during an indexing window. If a non-transactional full rebuild request is interrupted by network failure, the operator reruns the complete rebuild locally. Knowledge status reports current indexed-source progress from `knowledge_index_jobs.status = 'completed'`; `knowledge_source_settings.last_indexed_at` remains historical metadata and is used only for the latest-index timestamp. The browser polls uncached status every two seconds during synchronization and refreshes once more on every exit path. A source failure is stored and processing advances without an automatic retry; three consecutive failures stop the current administrator sync and return the remaining claimed sources to `pending`. Manual retry changes failed rows back to `pending` with a new `queued_at`, so they intentionally remain behind older pending work. New `last_error` values are bounded structured JSON containing the failure category, safe HTTP status/code when available, an upstream error excerpt of at most 1,500 characters, and a diary-content excerpt of at most 3,000 characters with original-length/truncation metadata. Authorization, bearer-token, API-key, access-token, and secret-like values are redacted. The column is service-role-only but contains private diary material; do not expose it through browser APIs or logs. Legacy rows can retain earlier generic or ModelScope-specific failure categories until retried.

The Phase 3 development baseline intentionally freezes the 598 sources whose index jobs were completed at the 2026-07-30 checkpoint. Seven sources were pending with no chunks or indexed-content hashes, and later daily diaries may add more pending jobs. Phase 3 development must snapshot exact eligible source IDs/content hashes, exclude pending or stale sources from coverage, and avoid presenting its result as the complete live diary corpus. After the feature is complete, process every remaining eligible index job and regenerate affected derived data before production acceptance.

Migration `supabase/migrations/20260730071934_phase3_theme_timeline.sql` implements the first Phase 3A slice and was applied to production on 2026-07-30 as Supabase migration `20260730080402_phase3_theme_timeline`:

- `understanding_observations` stores at most one proposed theme observation per run/source with fact/summary/inference classification and generation versions.

`create_theme_timeline_run()` briefly takes SHARE locks across the source/index tables, verifies both the approved count and corpus fingerprint, and atomically inserts all exact snapshot sources. Only completed/private/hashed sources with chunks enter the snapshot; pending, processing, failed, excluded, hashless, and missing-chunk sources cannot influence it. `claim_theme_timeline_source()` uses `FOR UPDATE SKIP LOCKED`, reclaims work after ten minutes, and marks a hash/status/scope mismatch stale before returning one source's current chunks. Completion, provider-stop release, failure, retry, final summary creation, and review are separate service-role-only RPCs. Source completion and evidence insertion are transactional and unique per run/source, so resume does not duplicate observations. Review rechecks live source hash, private scope, completed index status, and chunk presence before mutation.

New failed-source `understanding_run_sources.last_error` values are structured JSON kept below the existing 1,000-character RPC limit. They classify invalid input or structured model output with a bounded code such as invalid JSON, missing relevance, invalid classification, duplicate/unknown evidence, or prompt overflow. The diagnostic may contain a credential-redacted diary excerpt and model-output excerpt of at most 240 characters each, plus original-length/truncation metadata and a safe HTTP status when available. Legacy generic error strings remain readable only as `legacy` diagnostics. Phase 3 tables and GET routes remain administrator-only, but these excerpts still contain private diary material and must not be written to console logs or exposed to viewer/guest roles.

The native Ollama JSON Schema is generated per request. Extraction constrains `evidenceChunkIndexes` to the exact server-owned `knowledge_chunks.chunk_index` values for the claimed source and requires unique values; summary generation similarly constrains `observationIds` to the exact stored observation IDs available to that summary. This prevents paragraph ordinals or invented IDs from entering the database while retaining the independent application parser and transactional RPC validation as defense in depth. The constraint is an application response-format correction and requires no database migration.

## ModelScope daily call budget

Migration `supabase/migrations/20260720134848_modelscope_daily_quota.sql` adds the locked `modelscope_daily_usage` table and service-role-only `reserve_modelscope_api_call()` function. It was applied to production on 2026-07-20 as Supabase migration `20260720141701_modelscope_daily_quota`; the postflight preserved 595 source diaries, 595 knowledge jobs, and 210 chunks.

- One row stores the shared call count for each Beijing calendar date; `usage_date` is the primary key and `call_count` is constrained to `0–180`.
- Because calls made before migration cannot be reconstructed safely, the migration initializes its deployment date to 180. ModelScope remains stopped for that Beijing calendar day and starts normal counting with a new row after midnight.
- The `SECURITY INVOKER` RPC atomically inserts or increments the current date under the primary-key row lock. The 180th reservation succeeds; later reservations return `allowed = false` without increasing the count.
- The table has RLS enabled with no browser policy. PUBLIC, anon, and authenticated table/function access is revoked; only service-role server routes can reserve or inspect usage.
- Every ModelScope analysis, translation, or factual-answer generation HTTP attempt reserves before sending. Quota database errors fail closed, and OpenAI SDK automatic retries are disabled so a single reservation cannot silently create multiple provider attempts.
- Local knowledge Embedding and Workers-AI-only retrieval do not reserve or consume ModelScope quota. A factual-answer request with zero retrieved candidates returns insufficient evidence without preparing the provider or reserving a slot; a request with candidates reserves exactly once immediately before its single generation attempt.

Emergency removal is in `supabase/rollbacks/20260720134848_modelscope_daily_quota_rollback.sql`. Do not deploy Worker source that depends on the RPC after applying that rollback.

The two former global `storage.objects` policies were removed in Batch 5. Platform-owned relation ACLs remain unchanged, but RLS is enabled with no anon/authenticated policy:

- direct public object URLs are denied because the buckets are private;
- browser anon listing, upload, overwrite, and delete do not expose or mutate objects;
- authorized service-role APIs retain read/write/delete access;
- diary/yearly/audio proxy behavior remains unchanged.

### `2024To2025_diary_images`

- Diary images use `<year>/<yyyymmdd>_<index>.webp`.
- Browser compression limits width to 1920px and writes WebP at quality `0.8`.
- Relative paths are stored in `diaryContent.image_paths`.
- Upload uses `upsert: false`; a duplicate path fails instead of overwriting.
- Authorized diary replace/delete routes perform Storage cleanup and report residual paths when cleanup fails.

### `2025_Summary_Images`

- Yearly images use `yearly/<sequence>.webp`, where the server selects an unused numeric sequence.
- Relative paths are stored in `yearly_images.storage_path`.
- Replacing an image uploads a new object and updates the database reference through the authorized API.
- Authorized delete routes perform DB-first deletion and report any object path that still needs cleanup.

### `audio_messages`

- The client and API accept MP3 (`audio/mpeg` with a `.mp3` filename) and impose a 50 MB limit.
- Object paths use `<timestamp>_<random>.<extension>`.
- Upload uses `upsert: false`.
- Authorized APIs compensate failed metadata writes and perform DB-first deletion with residual-path reporting.

Database-row and Storage-object changes are not transactional. Failed metadata writes can leave orphaned objects, and failed object cleanup must be handled manually.

## Access patterns

- Server APIs: diary reads/CRUD, AI analysis, translation, CSV, and media reads. Diary media has latest-five/viewer/admin authorization; yearly media is readable by every role; audio is admin-only and supports a single HTTP Range.
- Authorized APIs: media write/replace/delete and yearly-summary metadata require an admin Cookie plus Origin validation. Health reads require viewer or admin; health mutations require admin plus Origin validation. Upload metadata failures trigger storage compensation; DB-first deletes report remaining object paths when cleanup fails. Anonymous-message reads and writes use the same-origin API; POST is public, Origin-checked, and rate-limited.
- Request validation: server routes stream JSON/multipart bodies through centralized byte limits, then validate field lengths, dates, arrays, file sizes, MIME types, and extensions before Supabase writes.
- CSV export: `/api/diary-download` is admin-only and queries through the server service-role client.
- Pagination: diary/messages use exact counts and `.range()`.
- Search: diary `content`/`subtitle` use OR `ilike`.
- Private knowledge search: administrator-only POST APIs create a normalized 1024-dimensional query embedding through the Workers AI Qwen3 binding, request exactly 20 candidates from the existing service-role-only hybrid RPC, apply date and private-scope filters, and preserve its cosine/literal Chinese exact-text fusion. The Workers AI BGE reranker scores date/title/content contexts and returns up to five results. The server then merges adjacent candidate chunks, removes duplicated overlap, and limits each diary to at most two independent results. Results include source date/title, merged chunk range, character offsets, diary ID, vector similarity, reranker score, and a response-level `rerankApplied` flag. An explicit administrator diagnostic request additionally returns the RPC-ordered candidates with fusion rank/vector similarity/RPC score, plus the raw valid reranker order and original candidate numbers before merging. It never returns the query vector. Reranker failures keep candidate diagnostics, leave the raw reranker stage empty, and fall back to vector-similarity order; no schema, RPC signature, vector database, or stored document embedding changes are required.
- Factual knowledge answers: administrator-only `POST /api/knowledge/answer` reuses the private search function directly and passes at most five final excerpts to ModelScope. The server assigns citation IDs, accepts only validated structured output, and resolves accepted IDs back to the retrieved server-owned source metadata. Unknown, duplicate, missing, or inconsistent model citation IDs are rejected. Insufficient evidence returns a fixed non-answer. This flow reads existing knowledge tables/RPCs but adds no answer, citation, conversation, summary, or derived-memory table and performs no persistence write.
- Phase 3 theme timeline: administrator-only `GET/POST /api/knowledge/understanding` reads stored runs and drives the explicit lifecycle. Create/process/retry/regenerate-summary and 3D generate-comparison actions are local-development-only; summary/observation/comparison-finding review and deterministic aggregate regeneration are Origin-checked administrator mutations. Extraction processes every eligible frozen source in the selected range rather than Top-K search results. One source is claimed per request and sent once to the run's frozen local Ollama model; a non-empty set of observations triggers one final Ollama summary call. An irrelevant result with null statement and empty evidence persists no observation; if it retains a recognized classification label, the server canonicalizes that field to null, while substantive payload still fails validation. After an observation edit/rejection invalidates that summary, regeneration is available only when every observation is confirmed, edited, or rejected; it makes one new local Ollama call over confirmed/edited observations when any remain, otherwise emits a deterministic no-retained-observation statement, and never reruns diary extraction. Phase 3C aggregation is separate: it makes no provider call, uses only confirmed/edited observations from one completed non-stale run, and persists PostgreSQL-derived source coverage, observation counts, distinct diaries, first/last dates, monthly groups, versions, and observation/evidence provenance. Phase 3D compares two nonempty months within one such aggregate using all frozen reviewed observations from both sides, never a Top-K sample or independent-run merge, then stores only parser-validated proposed findings with two-sided evidence links. Dynamic source/index hash, observation-version, aggregate, period, and finding-link checks expose stale derived records without overwriting history.
- Cache: yearly summaries use an in-memory per-year cache until the corresponding mutation invalidates it. Offline diary writes and the compressed `localStorage` backup have been removed.

Never substitute a service-role key for `SUPABASE_ANON_KEY`. The privileged client is `lib/server/supabaseAdmin.ts`, uses the separate server-only `SUPABASE_SERVICE_ROLE_KEY`, and must be called only from authorized routes.

- bucket visibility, MIME/size settings, listing, upload, overwrite, and delete behavior;

- knowledge embedding model/dimension consistency, queue retry/reclaim behavior, and RPC EXECUTE grants;
